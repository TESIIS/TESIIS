## P0 — 影響正確性與可用性

### P0-1 核子事故是一條死路，且以最危險的方式失敗

> 驗證方式：curl 實測

`核子事故` 這個欄位走完了 mapper → snapshot CSV → API response 的全程，每一筆回應都帶著它，資料裡也確實有 30 筆為 `Y`。但它**沒有任何查詢入口**：英文與中文參數都被靜默忽略，group 參數則直接 400。

| 請求 | 回傳 total | 應為 |
|---|---|---|
| `/api/shelters?limit=0` | 5854 | 5854 |
| `/api/shelters?nuclear=Y` | **5854** | 30 |
| `/api/shelters?核子事故=Y` | **5854** | 30 |
| `/api/shelters?disasters=nuclear` | **HTTP 400** | HTTP 200 |
| payload 中實際 `核子事故=='Y'` | 30 | — |

後果具體而言是：問「哪些收容所可以應對核子事故」，系統回你全部 5,854 筆，而且沒有任何跡象顯示篩選未生效。使用者會認為這 5,854 筆全部適用。

> **修復**：兩張 alias 表、`_hazardValue`、Flutter 的 model／篩選字彙／chip 全部補齊。
> 實測 `?nuclear=Y` 與 `?核子事故=Y` 皆回 **30**，`?disasters=nuclear` 回 **200**。

位置：

- `server/lib/presentation/controllers/shelter_controller.dart:105` — `_hazardAliases` 無 `nuclear`
- `server/lib/presentation/controllers/shelter_controller.dart:119` — `_groupAliases['disasters']` 無 `nuclear`
- `server/lib/domain/services/shelter_service.dart:72` — `_hazardValue` 無 `'核子事故'` case
- `flutter_codefest/lib/data/models/shelter.dart` — 完全無此欄位，parse 時丟棄
- `flutter_codefest/lib/domain/shelter_filters.dart:8` — 無對應的 filter chip

### P0-2 無法辨識的 hazard 值會靜默回傳全部資料

> 驗證方式：curl 實測

`shelter_service.dart:122-125` 在遇到看不懂的查詢值時設 `ok = true`，等於把這個條件視為未設定。這讓一個打錯字的篩選變成「不篩選」，而非錯誤。

```text
GET /api/shelters?flood=BOGUS&limit=0            → total 5854
GET /api/shelters?flood=BOGUS&match=or&limit=0   → total 5854
GET /api/shelters?limit=0                        → total 5854   (未篩選基準)
```

與 P0-1 是同一類錯誤，只是觸發路徑不同：**使用者要求的篩選沒有被套用，系統卻回應 200 與完整結果。**「只看防洪收容所」打錯一個字，就變成「全部收容所」。

> **修復**：值的驗證移到 request 邊界，比照既有的 `bboxError`／`groupError`。
> 實測 `?flood=BOGUS` 回 **400**（訊息列出合法值），`?flood=Y` 仍正常回 **4962**。
> `ShelterService` 保留寬鬆的 domain 行為，那是 `shelter_service_test.dart` 刻意釘住的。

### P0-3 全專案沒有任何 HTTP timeout，讓整套降級設計失效

> 驗證方式：grep 全域 + 讀碼

`server/lib`、`server/bin`、`flutter_codefest/lib` 三處 grep 不到任何 `.timeout(` 或 `connectionTimeout`。兩個對外呼叫都是裸的：

```text
server/lib/data/datasources/external/nfa_shelter_api.dart:21
    final resp = await _client.get(uri);            ← 無 timeout

flutter_codefest/lib/data/datasources/api.dart:33
    final response = await http.get(url);           ← 無 timeout
```

關鍵在於這是**「掛住」而非「失敗」**的情境。上游失敗時既有的降級設計運作良好；上游掛住時，整套設計會逐層失效：

1. `shelter_repository_impl.dart:100` 的 `_inFlight` 去重，會讓後續每一個請求都掛在同一個永不 resolve 的 future 上。
2. `catch` 進不去 → `_retryNotBefore` 永不設定 → backoff 機制從未生效。
3. client 端 `loadClusters` 的離線快取 fallback 寫在 `catch` 裡，因此**永遠不會執行**；使用者看到的是一個永遠轉不完的 spinner，而不是快取資料。

Docker 部署下 nginx 的 `proxy_read_timeout 30s` 會回 504 遮掩部分症狀，但 server 端那個 future 仍然掛著。若 API 直接對外暴露，則是無限期掛住。

> **修復**：新增 `UPSTREAM_TIMEOUT_SECONDS`（預設 15s，非正值一律夾回預設而非解除限制），
> client 端固定 15s。新增三個「上游掛住」的 repository 測試（MockClient 永不回應）——
> 在修好之前，這三個測試會直接卡死而不是失敗。

### P0-4 使用者 GPS 座標會寫進 log，與 SECURITY.md 的承諾矛盾

> 驗證方式：實測 log 輸出

`bin/server.dart:88` 的 `logRequests()` 記錄完整 query string。本次稽核期間產生的 log 可直接佐證：

```text
2026-08-23T19:22:47.103309  GET [200] /api/shelters?nuclear=Y&limit=0
2026-08-23T19:22:47.247436  GET [200] /api/shelters?flood=BOGUS&match=or&limit=0

同理，/api/shelters/nearby?lat=25.03&lng=121.56 會被逐字記錄。
```

但 SECURITY.md 寫「GPS 座標**只留在裝置端**⋯server 不記錄」，同一份文件後段卻又承認 log「可能含使用者查詢內容與來源 IP」。兩段自相矛盾，且對外承諾的那一段是錯的。

> **修復**：換成只記錄 method、path、status 與耗時的 middleware。實測對
> `/api/shelters/nearby?lat=…&lng=…` 送出請求後，log 中 `lat=`／`lng=`／`q=` 出現次數為 **0**。
> 代價是 debug 時看不到查詢參數；4xx 仍會在自己的 response body 說明原因。

## P1 — 演算法與 payload

### P1-5 前後端兩份 clustering 都把 Web Mercator 的 cos 用反了

> 驗證方式：數值驗證

Web Mercator 下 `dy_px/dφ = worldPx/(2π·cos φ)`，因此「每像素對應的緯度度數」等於每像素經度度數**乘以** `cos(φ)`。兩份實作都寫成了除：

```dart
// shelter_service.dart:275  ·  marker_clustering.dart:91-92
final cellLat = (lngPerPixel * cellPixels)
              / math.cos(latRad).abs().clamp(0.01, 1.0);
//            ↑ 應為 *
```

數值驗證（目標 80×80 px，各 zoom 結果一致）：

| 緯度 | 實際格高 | 偏差 |
|---|---|---|
| 22.0°N（屏東） | 93.1 px | 1.163× |
| 23.5°N（中部） | 95.1 px | 1.189× |
| 25.1°N（臺北） | 97.6 px | 1.219× |
| 26.4°N（連江） | — | 1.246× |

因為前後端**同步錯誤**，兩邊仍然彼此一致，`marker_clustering_test.dart` 因此沒有抓到。

> **修復時的更正**：上表是「名目 cell 大小」的比值。實際的 bucket index 是
> `lat / cellLat(lat)`，會多帶一項導數，真正的誤差比表中更大——**屏東 1.38×、連江 1.53×**。
> 而且只把 `cos` 反過來乘並不夠，那只會變成 0.83〜0.87×。
>
> **實際修法**：改成在 Web Mercator world 座標（0..1）分桶，cell 天生就是正方形，
> 不再需要逐點三角函數，程式也比原本短。前後端同步修改，兩邊各新增
> 四個緯度／zoom 組合的「螢幕上是否為 80px 正方形」斷言——這才是能抓到這類 bug 的斷言，
> 原本在度數空間的測試看不到。

### P1-6 stats 端點有 95.3% 的 payload 沒有任何消費者

> 驗證方式：curl 實測 + 讀碼

資料品質頁一開啟就送出無參數的 `GET /api/shelters/stats`。實測這個回應的組成：

```text
whole body        : 1,609,270 bytes
villages[] blocks : 1,534,027 bytes  (95.3%)  across 8,787 village entries
townships         : 367
```

而唯一的消費者 `flutter_codefest/lib/data/models/region_coordinate_stats.dart:39-47` 只讀 `byRegion[*].townships[*].coordinateQuality`，**從不碰 `villages`**。

這正是 `includeItems` / `includeShelters` 想解決的問題，只是當時少做了一層——village 才是真正的大宗。

> **修復**：加上 `includeVillages`（預設 false），`?include=villages` 才回傳。
> 實測預設回應 **1,452,859 → 63,440 bytes**，367 個 township 完整保留。

### P1-7 Cluster 展開半徑比格子本身大一個數量級

> 驗證方式：幾何推算 + 讀碼

`map_constants.dart:53` 的 `clusterExpandRadiusMeters = 250`，但 zoom 19 的格子實際只有約 **22 m × 26 m**。

`_showClusterMembers` 以 cluster 質心加 250 m 半徑打 `/shelters/nearby`，因此**會撈進鄰近格子的收容所**——那些本來是各自獨立的 cluster。同時因為 `limit: cluster.count`，真正的成員可能被更靠近質心的非成員擠掉。

原註解宣稱 “tight enough not to pull in unrelated shelters”，與實際尺度相差約十倍。

> **修復**：下修為 **60 m**，由 cell 對角線（約 30.5 m）推導而來，並在註解寫明推導過程。
